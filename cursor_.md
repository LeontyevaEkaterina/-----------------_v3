## ТЗ на создание веб‑приложения «Чат с нейросетями»

### 1. Общие положения и цели

- **Цель проекта**:  
  Создать кроссплатформенное веб‑приложение «Чат с нейросетями», доступное в браузере на ПК и мобильных устройствах (Android/iOS) через адаптивный интерфейс и PWA. Приложение позволяет пользователю после авторизации через Google‑аккаунт вести диалоги в реальном времени (со стримингом ответов) с различными популярными LLM/нейросетями и переключаться между ними «на лету».

- **Основной стек технологий**:
  - **Backend**: FastAPI (Python), соблюдение PEP 8.
  - **Frontend**: React + TypeScript + Tailwind CSS.
  - **Потоковый ответ**: SSE (Server-Sent Events).
  - **БД**: PostgreSQL (основная реляционная БД).
  - **Запуск**: через Docker и docker compose одной командой, по умолчанию порт 8080 на Windows.

- **Целевая платформа**:
  - Современные браузеры: Chrome, Edge, Firefox, Safari (включая мобильные версии).
  - PWA‑режим: установка на домашний экран Android и iOS, офлайн‑страница, корректное поведение в iOS Safari и Android Chrome.

- **Ограничения и честность**:
  - Приложение **не гарантирует бесплатный доступ ко всем моделям**.  
    «Бесплатно насколько возможно» достигается за счёт:
    - локальных моделей без ключей;
    - возможности пользоваться собственными ключами (BYOK);
    - опциональных админских ключей с лимитированным демо‑доступом.
  - Запрещается использовать неофициальные обходы блокировок, парсинг веб‑интерфейсов и иные сомнительные методы.

### 2. Авторизация и безопасность

#### 2.1. Поток авторизации через Google OAuth

- **Метод авторизации**:  
  Вход в приложение осуществляется **исключительно** через Google OAuth 2.0 (Authorization Code Flow с использованием PKCE либо стандартный серверный код‑флоу – уточнить на этапе реализации, но в ТЗ заложить поддержку безопасного варианта).

- **Базовый сценарий**:
  1. Пользователь на фронтенде нажимает кнопку «Войти через Google».
  2. Фронтенд перенаправляет пользователя на страницу авторизации Google с параметрами:
     - идентификатор клиента;
     - запрошенные scopes (минимально необходимые для получения email/профиля);
     - redirect URI, указанный в настройках OAuth‑клиента.
  3. После успешной авторизации Google перенаправляет пользователя на backend‑эндпойнт с **authorization code**.
  4. Backend обменивает code на access token (и refresh token, если используется) с серверами Google.
  5. Backend получает данные профиля пользователя (id, email, имя, аватар).
  6. Backend:
     - создаёт запись пользователя в БД при первом входе;
     - обновляет данные при последующих входах;
     - генерирует собственный JWT/сессионный маркер для доступа к API.
  7. JWT/сессионный маркер передаётся фронтенду и сохраняется **в httpOnly secure‑cookie** (желательно с флагами SameSite и Secure) или в аналогичном безопасном механизме. Хранение в localStorage **не допускается**.

- **Типы токенов в приложении**:
  - **JWT доступа (access token)**:
    - Содержит идентификатор пользователя, роль (user/admin), срок действия (короткий, например 15–60 минут).
    - Подписывается серверным секретом, хешируется и/или шифруется по необходимости.
  - **Refresh‑токен** (опционально):
    - Может храниться в отдельной httpOnly‑cookie с более долгим сроком действия.
    - На его основе backend выдаёт новый access token без повторной авторизации через Google.
    - Должен быть привязан к устройству/сессии, ревокация при logout или подозрительной активности.

- **Logout**:
  - Фронтенд вызывает соответствующий backend‑эндпойнт (например, `auth/logout`).
  - Backend:
    - инвалидирует refresh‑токен (удаляет или помечает как недействительный в БД);
    - очищает/истекает httpOnly‑cookie с JWT/refresh.
  - При необходимости дополнительно может предлагаться выход и на стороне Google (опционально, но не как обязательное требование).

#### 2.2. Роли и права доступа

- **Роли**:
  - **user**:
    - Может создавать, просматривать, редактировать и удалять только **свои** диалоги и сообщения.
    - Может просматривать список доступных провайдеров и моделей с учётом ограничений.
    - Может управлять личными настройками (системный промпт, параметры генерации, BYOK‑ключи, если включено).
  - **admin**:
    - Имеет доступ к административной панели/эндпойнтам:
      - просмотр и управление списком провайдеров и моделей;
      - настройка лимитов и квот;
      - управление админскими ключами провайдеров;
      - просмотр агрегированных логов запросов (без утечки чувствительных данных).
    - Доступ к диагностике и health‑информации (расширенный healthcheck).

- **Контроль доступа**:
  - Все защищённые эндпойнты должны проверять JWT/сессию и роль.
  - Используется централизованный middleware/зависимость авторизации.

#### 2.3. Требования к безопасности

- **CSRF**:
  - При использовании cookie‑базированной авторизации применяются **CSRF‑токены**:
    - выдаются на фронтенд (например, через отдельный эндпойнт или header);
    - передаются во всех изменяющих запросах (POST/PUT/PATCH/DELETE) в заголовке.
  - Альтернативный вариант: использование строгого SameSite‑режима cookie и только XHR‑запросов с корректным Origin/Referer.

- **XSS**:
  - Никакого хранения/рендеринга HTML от пользователя без экранирования.
  - Контент сообщений чата отображается как текст с безопасным форматированием.
  - Tailwind/React использовать стандартные безопасные практики, избежать `dangerouslySetInnerHTML` без строгой необходимости.

- **CORS**:
  - Backend должен быть настроен:
    - на ограниченный список разрешённых Origin (URL фронтенда);
    - на разрешённые методы и заголовки;
    - на поддержку credentails, если используется cookie‑авторизация.

- **Хранение токенов и секретов**:
  - Все секреты (Google OAuth client secret, JWT secret, админские API‑ключи, ключи пользователей BYOK) хранятся:
    - в переменных окружения;
    - в БД в зашифрованном и/или захешированном виде, где применимо.
  - Доступ к секретам строго ограничен на уровне ролей и эндпойнтов.

- **Общие требования**:
  - Обязательное использование HTTPS в боевом окружении.
  - Логирование без записи полных токенов и без чувствительных данных пользователя.
  - Регулярная ротация ключей и секретов (описать как организационное требование).

### 3. Чат и пользовательский опыт (UX)

#### 3.1. Основной интерфейс чата

- **Структура экрана чата**:
  - **Левая панель**:
    - Список диалогов пользователя:
      - название диалога;
      - дата/время последнего сообщения;
      - активный диалог выделен визуально.
    - Кнопки:
      - создание нового диалога;
      - поиск по диалогам (опционально).
  - **Центральная область**:
    - История сообщений выбранного диалога (по аналогии с современными мессенджерами).
    - Сообщения разделяются на «пользователь» и «модель», различимы по визуальному оформлению.
  - **Нижняя панель**:
    - Поле ввода сообщения.
    - Кнопка отправки.
    - Кнопки/селекторы выбора провайдера и модели (если не вынесены в правую панель).
    - Кнопка остановки текущей генерации (если идёт стриминг).

- **Операции над диалогами**:
  - **Создание**: новый диалог, с возможностью сразу задать системный промпт (по умолчанию – стандартный).
  - **Переименование**: изменение названия диалога.
  - **Удаление**: удаление диалога вместе с сообщениями (с подтверждением).
  - **История сообщений**: подгрузка по страницам при прокрутке вверх, если сообщений много.

#### 3.2. Стриминг ответа (SSE) и UX

- **Поведение фронтенда**:
  - После отправки запроса к модели фронтенд:
    - сразу добавляет сообщение пользователя;
    - создаёт «пустой» или «черновой» ответ модели, который будет заполняться по мере прихода событий SSE.
  - На время генерации отображается статус «печатает…» или аналогичный индикатор.
  - Каждый полученный фрагмент (token/delta) добавляется к текущему ответу в реальном времени.
  - При получении события окончания (done) индикатор снимается.

- **Остановка генерации**:
  - Пользователь может нажать кнопку «Остановить»:
    - фронтенд отправляет на backend запрос отмены (по request_id);
    - backend по возможности прерывает запрос к провайдеру;
    - SSE‑поток закрывается с соответствующим событием (например, error или done со статусом «cancelled»).

#### 3.3. Системный промпт и настройки

- **Системный промпт**:
  - Может задаваться:
    - на уровне **диалога** (отдельное поле);
    - и/или на уровне **профиля пользователя** (дефолтный стиль общения, который можно переопределять в конкретном диалоге).
  - UI:
    - страница/модальное окно настроек диалога с редактированием системного промпта;
    - визуальное напоминание, что у диалога установлен особый системный промпт (например, иконка).

- **Параметры генерации**:
  - Минимальный набор:
    - температура;
    - максимальное количество токенов;
    - топ‑p, топ‑k (если поддерживает модель);
    - дополнительные настройки по возможностям конкретного провайдера.
  - Параметры могут:
    - иметь глобальные значения по умолчанию;
    - переопределяться в рамках диалога или запроса.
  - UI:
    - компактная панель настроек рядом с выбором модели;
    - сохранение/сброс на дефолтные значения.

#### 3.4. Мобильная адаптация и PWA

- **Responsive UI**:
  - Интерфейс должен корректно работать на:
    - смартфонах с малым экраном;
    - планшетах;
    - десктопах.
  - Логика адаптации:
    - на мобильных устройствах список диалогов скрывается за «гамбургер‑меню»;
    - основной акцент – на области сообщений и поле ввода.

- **PWA‑поддержка**:
  - Наличие манифеста приложения с:
    - иконками для различных размеров экранов и платформ;
    - названием и кратким описанием;
    - цветами темы.
  - Реализация service worker для:
    - кэширования основных статических ресурсов;
    - предоставления **офлайн‑страницы** с сообщением о недоступности сети;
    - корректной работы установленных экземпляров приложения.

- **Особенности iOS и Android**:
  - Учесть:
    - специфики работы PWA в iOS Safari (ограничения по фоновому времени, обновлению service worker, поведению cookie);
    - уведомить пользователя при необходимости о ручных шагах установки на домашний экран.
  - Убедиться, что:
    - cookie‑авторизация и CORS корректно работают в мобильных браузерах;
    - не возникает проблем с редиректами OAuth на мобильных устройствах.

  Для каждой модели в системе должны храниться и отображаться:
  - поддержка стриминга (да/нет);
  - лимиты (например, макс. токены на запрос, разрешённое число запросов);
  - доступность в регионе (доступно/заблокировано/неизвестно);
  - необходимость ключа (обязателен ключ, поддерживается BYOK, доступен через админские ключи, доступен без ключа при локальном запуске);
  - ориентировочная стоимость или флаг «платная/бесплатная» (без внешних ссылок и без гарантий – именно как флаг/подсказка);
  - статус: в работе, временно недоступна, только для админских ключей и т.п.

#### 4.2. Абстракция «Provider Adapter»

- **Цель**:  
  Обеспечить единый интерфейс для обращения к различным LLM‑провайдерам, чтобы:
  - фронтенд не зависел от конкретных API провайдеров;
  - добавление нового провайдера не требовало переписывания ядра.

- **Требования к адаптерам**:
  - Единый контракт на backend‑уровне:
    - метод для отправки запроса;
    - поддержка стриминга через SSE;
    - обработка ошибок и таймаутов;
    - возврат унифицированной структуры ответа (метаданные, токены/фрагменты, статусы).
  - Каждый адаптер отвечает за:
    - преобразование унифицированного запроса в формат конкретного провайдера;
    - авторизацию (подстановку ключей: BYOK или админский);
    - интерпретацию ответа в унифицированный формат.

- **Регистрация и конфигурация**:
  - Централизованный реестр провайдеров и моделей:
    - конфигурируется через конфиг‑файл и/или БД;
    - позволяет включать/отключать провайдеры без изменения кода.

#### 4.3. Ограничения доступности в России и graceful degradation

- **Ограничения**:
  - Некоторые провайдеры и их домены могут быть недоступны в РФ без VPN.
  - Приложение должно стремиться работать **без VPN**, используя:
    - локальные модели;
    - провайдеров, официально доступных в регионе.

- **Стратегия graceful degradation**:
  - **Авто‑детект недоступности**:
    - обработка сетевых ошибок при обращении к API провайдера;
    - ведение статистики неудачных запросов (по коду/таймауту);
    - временное помечание провайдера/модели как «недоступна» для конкретного региона/пользователя.
  - **Сообщения пользователю**:
    - чёткие и понятные:
      - «Провайдер временно недоступен из вашего региона»;
      - «Попробуйте другую модель или локальный режим».
  - **Предложение альтернатив**:
    - если модель недоступна:
      - автоматически предлагать доступных провайдеров;
      - предлагать локальные модели при наличии.
  - **Запрет обходов**:
    - не предлагать:
      - использование сторонних прокси‑служб, нелегальных обходов блокировок;
      - парсинг веб‑интерфейсов и браузерные хаки.

### 5. Режимы доступа к моделям и ограничение затрат

#### 5.1. Реальность ограничений

- **Фиксация в ТЗ**:
  - Большинство облачных LLM требует:
    - отдельный API‑ключ;
    - учётную запись;
    - возможную оплату.
  - Приложение **не может** гарантировать бесплатный доступ ко всем этим моделям.

#### 5.2. Режим A: Локальные модели без ключей

- **Описание**:
  - Базовый бесплатный режим.
  - Модели запускаются:
    - локально на машине пользователя;
    - либо на сервере владельца проекта (например, через отдельный сервис‑рантайм).
  - Поддерживаемые модели:
    - варианты Llama, Qwen, Mistral и др., доступные для локального развёртывания.

- **Требования**:
  - Backend должен уметь обращаться к локальному рантайму через унифицированный адаптер.
  - В интерфейсе явно указывать, что модель:
    - работает локально;
    - не требует ключа;
    - может иметь ограничения по качеству/скорости.

#### 5.3. Режим B: BYOK (bring your own key)

- **Описание**:
  - Пользователь может добавить собственные ключи провайдеров:
    - ключи не видны другим пользователям;
    - используются только для запросов от этого пользователя.

- **Хранение и безопасность**:
  - Ключи хранятся:
    - в БД в зашифрованном виде;
    - с минимальным набором метаданных (какому провайдеру принадлежит).
  - UI должен:
    - позволять добавлять/редактировать/удалять ключи;
    - не отображать ключ полностью после сохранения (маскирование).
  - Backend обязан:
    - валидировать ключ при первом использовании (по возможности);
    - логировать ошибки без раскрытия ключа.

#### 5.4. Режим C: Админские ключи

- **Описание**:
  - Администратор проекта может настроить глобальные ключи провайдеров:
    - используются для демо‑режима;
    - применяются для всех или части пользователей.
  - Возможны ограничения:
    - допустимое число запросов в день;
    - ограничение списка моделей.

- **Контроль и бюджетные предохранители**:
  - Админские ключи должны иметь:
    - глобальные лимиты (например, X запросов/день);
    - алерты/логи расхода.
  - При достижении лимита:
    - соответствующие модели становятся недоступны;
    - пользователю отображается сообщение с предложением альтернатив (локальные модели или BYOK).

#### 5.5. Лимитирование и защита от злоупотреблений

- **Rate limit и квоты**:
  - На уровне backend:
    - ограничение количества запросов в минуту/час для каждого пользователя;
    - отдельные лимиты для разных режимов (локальные, BYOK, админские ключи).
  - На уровне провайдеров:
    - учёт лимитов, заданных внешним API, чтобы не превышать.

- **Механизмы**:
  - Использование счётчиков в БД или in‑memory‑хранилище (например, Redis):
    - по user_id;
    - по типу провайдера/ключа.
  - Реакция при превышении:
    - возврат ошибки с понятным сообщением;
    - недопуск дальнейших запросов до истечения окна.

- **Защита от злоупотреблений**:
  - Обнаружение подозрительных паттернов:
    - аномально высокое число запросов;
    - многочисленные ошибки авторизации;
    - попытки обхода лимитов.
  - Возможность блокировки пользователя/ключа на уровне admin‑панели.

### 6. Данные и хранение

#### 6.1. Типы данных

- **Пользователь**:
  - идентификатор (внутренний и Google);
  - email, имя, аватар;
  - роль (user/admin);
  - настройки профиля:
    - системный промпт по умолчанию;
    - параметры генерации по умолчанию;
    - выбранная цветовая тема (светлая/тёмная);
    - предпочтительные провайдеры/модели.

- **Диалог (чат)**:
  - идентификатор;
  - пользователь‑владелец;
  - название диалога;
  - системный промпт (опциональный, перекрывающий профильный);
  - дата создания и обновления;
  - текущие настройки генерации (если переопределены).

- **Сообщение**:
  - идентификатор;
  - ссылка на диалог;
  - тип (user/model/system);
  - текст сообщения;
  - провайдер и модель, использованные для ответа (для сообщений модели);
  - временные метки (создано, обновлено).

- **Ключи провайдеров**:
  - ключи пользователей (BYOK);
  - админские ключи;
  - связанный провайдер и список моделей (если применимо);
  - зашифрованное значение;
  - статус (активен/отключён).

- **Логи запросов**:
  - request_id;
  - пользователь;
  - диалог;
  - провайдер/модель;
  - время начала и окончания;
  - статус (успех, ошибка, отмена, таймаут);
  - метаданные (включая сокращённую/анонимизированную информацию о запросе).

#### 6.2. БД и миграции

- **Рекомендуемая БД**: PostgreSQL.
- **Миграции**:
  - Обязательное использование системы миграций (например, Alembic или аналог).
  - Миграции хранятся в отдельной папке и запускаются:
    - при развёртывании контейнеров;
    - либо отдельной командой.

#### 6.3. Политика приватности и логирование

- **Что логируем**:
  - технические метаданные запросов:
    - идентификаторы пользователей (или псевдонимные идентификаторы);
    - идентификаторы диалогов и сообщений;
    - провайдера и модель;
    - статус и длительность операции.
  - сообщения об ошибках без включения полных текстов пользовательских промптов, если это не требуется для диагностики (возможен лог усечённого текста по настройкам).

- **Что не логируем**:
  - полные тексты чувствительных сообщений по умолчанию;
  - полные токены доступа, ключи API, refresh‑токены.

- **Маскирование**:
  - При необходимости выводить фрагменты пользовательского ввода в логи:
    - использовать маскирование (например, часть текста, без персональных данных);
    - исключать потенциальные секреты (номера карт, пароли и т.п.).

- **Сроки хранения**:
  - Логи запросов:
    - ограниченный срок (например, 30–90 дней), далее архивация или удаление.
  - Пользовательские данные и истории диалогов:
    - до удаления пользователем или по политике (можно задавать конфигом).

### 7. Backend: архитектура, API и провайдеры

#### 7.1. Архитектура и модули backend

- **Слои**:
  - **API‑слой**:
    - FastAPI‑роутеры для:
      - авторизации;
      - пользователей;
      - чатов и сообщений;
      - стриминга (SSE);
      - провайдеров/моделей;
      - админских операций;
      - healthcheck.
  - **Сервисный слой**:
    - бизнес‑логика:
      - управление диалогами и сообщениями;
      - вызовы адаптеров провайдеров;
      - применение лимитов, квот, логирования.
  - **Слой доступа к данным (DAL/Repository)**:
    - работа с БД через ORM или низкоуровневый драйвер.
  - **Слой провайдеров (Provider Adapters)**:
    - отдельный модуль/пакет с реализациями адаптеров.

- **Общие требования**:
  - Строгая типизация Python‑кода с аннотациями типов.
  - Соблюдение PEP 8.
  - Разделение конфигурации по окружениям (dev/stage/prod).

#### 7.2. Эндпойнты

*(имена примерные, могут уточняться, но требования к функционалу жёсткие)*

- **Auth**:
  - `GET /auth/google/login` – инициирует OAuth‑флоу, отдаёт URL для редиректа.
  - `GET /auth/google/callback` – приём authorization code, обмен на токен, создание/обновление пользователя, установка сессии.
  - `POST /auth/logout` – выход пользователя, очистка cookie/сессии.
  - `GET /auth/session` – проверка текущей сессии, возвращает краткую информацию о пользователе.

- **Users**:
  - `GET /users/me` – текущий пользователь (email, роль, настройки).
  - `PATCH /users/me` – обновление настроек профиля (системный промпт, тема, дефолтные параметры генерации).
  - Эндпойнты для BYOK‑ключей:
    - `GET /users/me/keys` – список ключей (маскированный).
    - `POST /users/me/keys` – добавление ключа.
    - `DELETE /users/me/keys/{key_id}` – удаление ключа.

- **Chats**:
  - `GET /chats` – список диалогов пользователя.
  - `POST /chats` – создание диалога.
  - `GET /chats/{chat_id}` – данные диалога и, при необходимости, часть истории.
  - `PATCH /chats/{chat_id}` – переименование, изменение системного промпта и настроек.
  - `DELETE /chats/{chat_id}` – удаление диалога и сообщений.

- **Messages**:
  - `GET /chats/{chat_id}/messages` – история сообщений (с пагинацией).
  - `POST /chats/{chat_id}/messages` – отправка нового сообщения пользователя и запуск генерации ответа (может возвращать request_id и перенаправлять к SSE).

- **Streaming (SSE)**:
  - `GET /stream/{request_id}` – SSE‑эндпойнт для получения стрима токенов/фрагментов от модели.

- **Models/Providers**:
  - `GET /models` – список моделей с метаданными (провайдер, поддержка стриминга, статус доступности, необходимость ключа, флаги стоимости).
  - `GET /providers` – список провайдеров и их статуса.

- **Admin**:
  - `GET /admin/stats` – агрегированные статистики запросов, ошибок, использования ключей.
  - `GET /admin/providers` / `PATCH /admin/providers` – управление доступностью провайдеров и моделей.
  - `GET /admin/keys` / `POST /admin/keys` / `DELETE /admin/keys/{key_id}` – управление админскими ключами.
  - Дополнительные диагностические эндпойнты по необходимости.

- **Healthcheck**:
  - `GET /health` – базовый статус сервиса.
  - `GET /health/deep` (доступно только админам) – расширенный статус (доступность БД, провайдеров и т.п.).

#### 7.3. Формат SSE‑сообщений

- **Типы событий**:
  - **token/delta**:
    - содержит очередной фрагмент текста ответа;
    - включает метаданные (request_id, позиция, при необходимости – вероятность и т.п.).
  - **metadata**:
    - информация о модели, лимитах, оценочном бюджете и прочее.
  - **error**:
    - код ошибки;
    - человеко‑читаемое сообщение;
    - request_id.
  - **done**:
    - статус завершения (успешно, отменено, таймаут);
    - итоговые метаданные (число токенов, длительность).

- **Корреляция**:
  - Каждое событие должно содержать **request_id**, по которому фронтенд сопоставляет ответ с запросом.

- **Обработка reconnect**:
  - При обрыве SSE‑соединения фронтенд:
    - может попытаться переподключиться (при разумном лимите);
    - backend должен корректно:
      - либо продолжить стрим с текущего состояния (если возможно);
      - либо вернуть ошибку, если запрос уже завершён.

#### 7.4. Ошибки, таймауты, отмена генерации

- **Ошибки**:
  - Классификация:
    - ошибки клиента (невалидный запрос, превышение лимитов);
    - ошибки провайдера (отказ, лимит, невалидный ключ);
    - сетевые ошибки;
    - внутренние ошибки сервера.
  - API должно возвращать:
    - машино‑читаемый код;
    - человеко‑читаемое сообщение;
    - при SSE – событие типа error.

- **Таймауты**:
  - Устанавливать разумные таймауты:
    - на время ожидания ответа от провайдера;
    - на общее время генерации.
  - При таймауте:
    - генерация прерывается;
    - пользователю возвращается информация о таймауте.

- **Отмена генерации**:
  - Возможность прекратить запрос:
    - по инициативе пользователя (кнопка «Остановить»);
    - по лимитам/ограничениям.
  - Backend:
    - отменяет запрос к провайдеру, если API позволяет;
    - закрывает SSE‑поток с событием done со статусом «cancelled».

#### 7.5. Слой провайдеров: ретраи, наблюдаемость, тестируемость

- **Ретраи**:
  - При временных сетевых ошибках допускается ограниченное число повторов.
  - Не ретраить при ошибках авторизации, неверных ключах и жёстких лимитах.

- **Наблюдаемость**:
  - Логирование:
    - входа/выхода адаптера (без текстов запросов, кроме анонимизированных);
    - ошибок, таймаутов, отмен.
  - Трейсинг (по возможности):
    - кореляционные идентификаторы across запросов;
    - измерение времени обращений к провайдерам.

- **Тестируемость**:
  - Для каждого адаптера должны быть:
    - модульные тесты (mock внешнего API);
    - интеграционные тесты (по возможности, с тестовыми ключами).
  - Использовать интерфейс/абстракцию для адаптеров, чтобы подменять реализации в тестах.

### 8. Frontend: архитектура, страницы, SSE и UI

#### 8.3. Реалтайм‑поток SSE на фронтенде

- **Буферизация**:
  - При получении событие token/delta:
    - добавление полученного фрагмента в стейт;

### 11. Приёмка, чек‑лист и типичные ошибки

#### 11.1. Критерии приёмки

- **Авторизация Google**:
  - Успешный вход и выход;

  - статус «печатает…»;
  - возможность остановки генерации и корректное завершение.

- **Переключение моделей**:
  - Список провайдеров и моделей с метаданными;
  - смена модели в рамках диалога;
  - корректная обработка недоступных моделей.

- **Обработка недоступности в РФ**:
  - При попытке использовать заблокированный/недоступный провайдер:
    - отображается понятное сообщение;
    - предлагаются альтернативы (локальные/доступные модели);
    - никаких предложений по неофициальному обходу блокировок.

- **Мобильная адаптация и PWA**:
  - Корректное отображение на смартфоне;
  - удобный интерфейс чата;

  - Ограничения по числу запросов в разумных пределах;
  - корректная обработка превышения лимитов;
  - защита от злоупотреблений и аномальной активности.

- **Стабильность**:
  - Отсутствие критических ошибок при стандартных сценариях;
  - корректная обработка таймаутов и отмен;
  - работоспособность после перезапуска контейнеров.

#### 11.2. Типичные ошибки и диагностика

- **SSE‑проблемы**:
  - Соединение сразу закрывается:
    - проверить CORS;
    - проверить правильность пути к SSE‑эндпойнту;
    - убедиться, что backend корректно держит соединение.
  - Дубликаты сообщений:
    - проверить логику reconnect на фронтенде;
    - убедиться, что нет повторного запуска стрима на один request_id.

- **CORS**:
  - Ошибки в браузере:
    - проверить, что фронтенд‑origin добавлен в список разрешённых;
    - проверить заголовки `Access-Control-Allow-*`.

- **OAuth redirect URI**:
  - Ошибки после логина:
    - убедиться, что redirect URI на стороне Google совпадает с реальным;
    - проверить https/http и порты.

- **Cookie issues на iOS**:
  - Проблемы с сохранением сессии:
    - проверить флаги SameSite и Secure;
    - протестировать в режиме PWA и в обычном Safari;
    - при необходимости скорректировать конфигурацию CORS и cookie.

- **Прокси/SSL**:
  - Проблемы в боевом окружении:
    - убедиться, что reverse‑proxy корректно пробрасывает заголовки;
    - проверить сертификаты и цепочку доверия.

- **Таймауты и лимиты**:
  - Частые таймауты:
    - проверить таймауты подключения к провайдерам;
    - убедиться, что локальные модели настроены правильно и не перегружены.
  - Быстрое исчерпание лимитов:
    - проверить настройки rate‑limit и квот;
    - убедиться в отсутствии циклических повторных запросов на фронтенде.

    db: Annotated[Session, Depends(get_db)],
    token: Annotated[str, Depends()],
) -> User:
    """Resolve current user from JWT token (placeholder dependency).

    TODO: заменить на реализацию cookie/JWT-стратегии и Google OAuth.
    """
    credentials_exception = HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="Could not validate credentials",
    )
    try:
        payload = jwt.decode(
            token,
            settings.jwt_secret_key,
            algorithms=[settings.jwt_algorithm],
        )
        user_id: int | None = payload.get("sub")
        if user_id is None:
            raise credentials_exception
    except JWTError as exc:
        raise credentials_exception from exc

    user = db.query(User).filter(User.id == user_id).first()
    if user is None:
        raise credentials_exception
    return user

from datetime import datetime, timedelta, timezone
from typing import Any, Dict

from jose import jwt

from .config import get_settings


settings = get_settings()


def create_access_token(subject: str | int, extra_claims: Dict[str, Any]) -> str:
    """Create signed JWT access token."""
    now = datetime.now(tz=timezone.utc)
    expire = now + timedelta(minutes=settings.access_token_expires_minutes)
    payload: Dict[str, Any] = {
        "sub": str(subject),
        "iat": int(now.timestamp()),
        "exp": int(expire.timestamp()),
    }
    payload.update(extra_claims)
    return jwt.encode(
        payload,
        settings.jwt_secret_key,
        algorithm=settings.jwt_algorithm,
    )


def cookie_settings() -> dict[str, Any]:
    """Return common cookie settings for auth cookie."""
    return {
        "httponly": True,
        "secure": False,
        "samesite": "lax",
        "path": "/",
    }

from typing import Annotated

from fastapi import Cookie, Depends, HTTPException, status
from jose import JWTError, jwt
from sqlalchemy.orm import Session

from ..config import get_settings
from ..db import get_db
from ..models import User


settings = get_settings()


def get_current_user(
    db: Annotated[Session, Depends(get_db)],
    access_token: Annotated[str | None, Cookie(alias=settings.access_token_cookie_name)] = None,
) -> User:
    """Resolve current user from JWT stored in httpOnly cookie."""
    credentials_exception = HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="Could not validate credentials",
    )
    if not access_token:
        raise credentials_exception
    try:
        payload = jwt.decode(
            access_token,
            settings.jwt_secret_key,
            algorithms=[settings.jwt_algorithm],
        )
        sub = payload.get("sub")
        if sub is None:
            raise credentials_exception
        user_id = int(sub)
    except (JWTError, ValueError) as exc:
        raise credentials_exception from exc

    user = db.query(User).filter(User.id == user_id).first()
    if user is None:
        raise credentials_exception
    return user

@router.get("/google/callback")
async def google_callback(
    code: str,
    response: Response,
    db: Annotated[Session, Depends(get_db)],
) -> dict:
    """Handle Google OAuth callback, create user and issue session cookie."""
    if not settings.google_client_id or not settings.google_client_secret:
        raise HTTPException(
            status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
            detail="Google OAuth is not configured",
        )

    token_payload = {
        "code": code,
        "client_id": settings.google_client_id,
        "client_secret": settings.google_client_secret,
        "redirect_uri": settings.google_redirect_uri,
        "grant_type": "authorization_code",
    }

    async with httpx.AsyncClient(timeout=10) as client:
        token_resp = await client.post(
            settings.google_token_url,
            data=token_payload,
        )
        if token_resp.status_code != 200:
            raise HTTPException(
                status_code=status.HTTP_401_UNAUTHORIZED,
                detail="Could not exchange authorization code",
            )
        token_data = token_resp.json()

        id_token = token_data.get("id_token")
        access_token = token_data.get("access_token")
        if not id_token and not access_token:
            raise HTTPException(
                status_code=status.HTTP_401_UNAUTHORIZED,
                detail="Invalid token response from Google",
            )

        if id_token:
            claims = jwt.get_unverified_claims(id_token)
            sub = claims.get("sub")
            email = claims.get("email")
            name = claims.get("name")
            picture = claims.get("picture")
        else:
            userinfo_resp = await client.get(
                settings.google_userinfo_url,
                headers={"Authorization": f"Bearer {access_token}"},
            )
            if userinfo_resp.status_code != 200:
                raise HTTPException(
                    status_code=status.HTTP_401_UNAUTHORIZED,
                    detail="Could not fetch user info from Google",
                )
            info = userinfo_resp.json()
            sub = info.get("sub")
            email = info.get("email")
            name = info.get("name")
            picture = info.get("picture")

    if not sub or not email:
        raise HTTPException(
            status_code=status.HTTP_400_BAD_REQUEST,
            detail="Google did not provide required user data",
        )

    user = db.query(User).filter(User.google_sub == sub).first()
    if user is None:
        user = User(
            google_sub=sub,
            email=email,
            name=name,
            avatar_url=picture,
            role="user",
        )
        db.add(user)
        db.commit()
        db.refresh(user)
    else:
        user.email = email
        user.name = name
        user.avatar_url = picture
        db.add(user)
        db.commit()
        db.refresh(user)

    jwt_token = create_access_token(
        subject=user.id,
        extra_claims={"role": user.role},
    )

    response.set_cookie(
        key=settings.access_token_cookie_name,
        value=jwt_token,
        **cookie_settings(),
    )

    return {"status": "ok"}

- **Конфиг**:
  - В `config.py` добавлены параметры Google OAuth: `google_client_id`, `google_client_secret`, `google_redirect_uri`, URL’ы токен/профиль, список `google_scopes`, а также имя cookie с JWT (`access_token_cookie_name`).

- **JWT и cookie**:
  - В `security.py` реализованы:
    - `create_access_token(subject, extra_claims)` – выпуск JWT с `sub`, `iat`, `exp` и ролью.
    - `cookie_settings()` – общие параметры httpOnly‑cookie (для dev: `secure=False`, `samesite="lax"`).

- **Чтение текущего пользователя**:
  - В `api/deps.py` обновлён `get_current_user`:
    - Читает JWT из httpOnly‑cookie с именем из конфига.
    - Декодирует токен, достаёт `sub` (ID пользователя), находит пользователя в БД и возвращает его.
    - При отсутствии/ошибке токена выбрасывает `401`.

- **Эндпойнты авторизации (`api/routes_auth.py`)**:
  - `GET /api/v1/auth/google/login`:
    - Собирает и возвращает `authorization_url` Google OAuth (клиент, redirect_uri, scope и т.д.).
    - Фронтенд по этому URL делает редирект пользователя.
  - `GET /api/v1/auth/google/callback`:
    - Принимает `code`, обменивает его на токены через Google.
    - Получает данные пользователя (через `id_token` или `userinfo`), извлекает `sub`, `email`, `name`, `picture`.
    - Создаёт или обновляет пользователя в БД (`User` с `google_sub`, email, именем, аватаром, ролью `user`).
    - Выпускает JWT с `sub=user.id` и `role`.
    - Записывает JWT в httpOnly‑cookie (имя из настроек) и возвращает `{ "status": "ok" }`.
  - `GET /api/v1/auth/session`:
    - Считывает JWT из cookie, декодирует его, находит пользователя.
    - Если сессии нет или токен некорректен – возвращает `null`, иначе `UserMe`.
  - `POST /api/v1/auth/logout`:
    - Удаляет auth‑cookie и возвращает `204`, т.е. разлогинивает пользователя.

settings = get_settings()

OAUTH_STATE_COOKIE_NAME = "oauth_state"


@router.get("/google/login")
async def google_login(response: Response) -> dict:
    """Return Google OAuth authorization URL.

    Фронтенд получает URL и выполняет редирект пользователя.
    """
    state = token_urlsafe(32)
    response.set_cookie(
        key=OAUTH_STATE_COOKIE_NAME,
        value=state,
        max_age=600,
        **cookie_settings(),
    )

    params = {
        "client_id": settings.google_client_id,
        "redirect_uri": settings.google_redirect_uri,
        "response_type": "code",
        "scope": " ".join(settings.google_scopes),
        "access_type": "offline",
        "prompt": "consent",
        "state": state,
    }
    url = f"{settings.google_auth_base_url}?{urlencode(params)}"
    return {"authorization_url": url}


@router.get("/google/callback")
async def google_callback(
    request: Request,
    code: str,
    response: Response,
    db: Annotated[Session, Depends(get_db)],
) -> dict:
    """Handle Google OAuth callback, create user and issue session cookie."""
    state_query = request.query_params.get("state")
    state_cookie = request.cookies.get(OAUTH_STATE_COOKIE_NAME)
    if not state_query or not state_cookie or state_query != state_cookie:
        raise HTTPException(
            status_code=status.HTTP_400_BAD_REQUEST,
            detail="Invalid OAuth state",
        )

    if not settings.google_client_id or not settings.google_client_secret:
        raise HTTPException(
            status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
            detail="Google OAuth is not configured",
        )

    token_payload = {
        "code": code,
        "client_id": settings.google_client_id,
        "client_secret": settings.google_client_secret,
        "redirect_uri": settings.google_redirect_uri,
        "grant_type": "authorization_code",
    }

    async with httpx.AsyncClient(timeout=10) as client:
        token_resp = await client.post(
            settings.google_token_url,
            data=token_payload,
        )
        if token_resp.status_code != 200:
            raise HTTPException(
                status_code=status.HTTP_401_UNAUTHORIZED,
                detail="Could not exchange authorization code",
            )
        token_data = token_resp.json()

        id_token = token_data.get("id_token")
        access_token = token_data.get("access_token")
        if not id_token and not access_token:
            raise HTTPException(
                status_code=status.HTTP_401_UNAUTHORIZED,
                detail="Invalid token response from Google",
            )

        if id_token:
            claims = jwt.get_unverified_claims(id_token)
            sub = claims.get("sub")
            email = claims.get("email")
            name = claims.get("name")
            picture = claims.get("picture")
        else:
            userinfo_resp = await client.get(
                settings.google_userinfo_url,
                headers={"Authorization": f"Bearer {access_token}"},
            )
            if userinfo_resp.status_code != 200:
                raise HTTPException(
                    status_code=status.HTTP_401_UNAUTHORIZED,
                    detail="Could not fetch user info from Google",
                )
            info = userinfo_resp.json()
            sub = info.get("sub")
            email = info.get("email")
            name = info.get("name")
            picture = info.get("picture")

    if not sub or not email:
        raise HTTPException(
            status_code=status.HTTP_400_BAD_REQUEST,
            detail="Google did not provide required user data",
        )

    user = db.query(User).filter(User.google_sub == sub).first()
    if user is None:
        user = User(
            google_sub=sub,
            email=email,
            name=name,
            avatar_url=picture,
            role="user",
        )
        db.add(user)
        db.commit()
        db.refresh(user)
    else:
        user.email = email
        user.name = name
        user.avatar_url = picture
        db.add(user)
        db.commit()
        db.refresh(user)

    jwt_token = create_access_token(
        subject=user.id,
        extra_claims={"role": user.role},
    )

    response.set_cookie(
        key=settings.access_token_cookie_name,
        value=jwt_token,
        **cookie_settings(),
    )

    return {"status": "ok"}


@router.get("/session", response_model=UserMe | None)
async def get_session(
    request: Request,
    db: Annotated[Session, Depends(get_db)],
) -> UserMe | None:
    """Return current session information based on auth cookie."""
    token = request.cookies.get(settings.access_token_cookie_name)
    if not token:
        return None
    try:
        payload = jwt.decode(
            token,
            settings.jwt_secret_key,
            algorithms=[settings.jwt_algorithm],
        )
        sub = payload.get("sub")
        if sub is None:
            return None
        user_id = int(sub)
    except (JWTError, ValueError):
        return None

    user = db.query(User).filter(User.id == user_id).first()
    if user is None:
        return None
    return UserMe.model_validate(user)


@router.post("/logout", status_code=status.HTTP_204_NO_CONTENT)
async def logout(response: Response) -> None:
    """Logout by clearing auth cookie."""
    response.delete_cookie(
        key=settings.access_token_cookie_name,
        path="/",
    )
    return None

const App: React.FC = () => {

### Кратко

**Error Code: -102 на `http://localhost/` почти всегда означает `ERR_CONNECTION_REFUSED` — по этому адресу/порту просто ничего не слушает.**

### Почему так у тебя

В нашем проекте:

- В `docker-compose.yml` для фронтенда прописано:

  - `ports: - "8080:80"` → сайт доступен на `http://localhost:8080`, а не на `http://localhost/` (порт 80).  
- Когда ты заходишь на `http://localhost/` (порт 80), браузер стучится туда, там нет сервиса → соединение отклоняется → `-102`.

### Что сделать

1. **Открывай именно:**

   - `http://localhost:8080/`

2. Убедись, что контейнеры запущены:

   - в корне проекта: `docker compose up --build`
   - посмотри, что сервис `frontend` стартовал без ошибок, и nginx слушает `0.0.0.0:80` внутри контейнера.

3. Если `http://localhost:8080` тоже не открывается:

   - проверь, не занят ли порт 8080 другим процессом;
   - убедись, что Docker не блокируется фаерволом Windows.
